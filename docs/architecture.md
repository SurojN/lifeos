# Architecture

The production application is a Next.js App Router application at the repository root. React Server Components render the shell; sensitive operations remain in the Node.js runtime. Clerk verifies identity and sessions. The authentication adapter maps the Clerk identifier to LifeOS's internal `User.id`, which is the authorization identifier.

PostgreSQL is accessed through Prisma only from server-only database and repository modules. UI components do not receive unrestricted Prisma access. Repositories encode ownership in queries (`id` plus `userId`) and services validate input, apply authorization, perform the operation, and create audit records.

Private document bytes live outside PostgreSQL behind `PrivateStorage`. MinIO and production S3 share the same S3-compatible adapter. Object keys are generated by the backend under `users/{internalUserId}/documents/`; clients cannot choose keys. No public or presigned download URL exists in this phase.

The document lifecycle is `PENDING_UPLOAD` → `QUARANTINED` → `AVAILABLE`, with `REJECTED` and soft `DELETED` terminal outcomes. `DocumentUpload` separately records short-lived authorization and byte/checksum verification. Uploads use the same private service from the Documents, Medical, Finance, and Travel sections and carry an explicit document category. A consented `ExtractionJob` may call the configured server-side provider and move to review, but its encrypted output remains advisory. Extracted medical information remains `UNVERIFIED` until an explicit user-confirmation transaction creates or updates the medical record and its source-linked life event.

AI extraction is opt-in per request, records a consent entry, sends only the selected private source document to the configured provider, and stores structured output encrypted. Provider keys remain server-only. The initial adapter supports JPEG and PNG documents; unsupported formats fail visibly and leave the original document unchanged.

Confirmed medical records and their generated life events have a direct, one-to-one, tenant-consistent relationship. Corrections update both objects in one transaction; deletion soft-deletes both while retaining the private source document unless the owner separately deletes it. The management service recognizes older encrypted `medicalRecordId` metadata and attaches that legacy event on its next correction, or recreates a missing timeline event, so the additive migration does not discard existing history. Medical and timeline search runs in the already-loaded client page so sensitive search terms are not placed in URLs.

The dashboard converts authorized, decrypted repository results into a minimal serializable `GuideFact` contract. The first Life Guide evaluates questions locally in the loaded page, returns only confirmed or user-entered matches, includes provenance and source links, and refuses when no evidence matches. It makes no external model request. A future language-model adapter may improve phrasing or planning only if the server verifies every returned fact/source ID against this grounded contract and records explicit consent.

The historical Vite prototype under `prototype/` is reference material only and shares no production runtime code.

## Appointment preparation

The Appointments server page authenticates the owner through the existing adapter, reads that owner's medical records, filters to `USER_CONFIRMED`, and sends an explicit display contract to the preparation component. The browser includes only records the user selects, preserves their source filenames and IDs, and labels medicines as historical source information rather than current use. Purpose and questions are user-entered. The preview and plain-text download use the same pure transformation, covered by selection and provenance tests. Drafts live only in React state; this feature adds no storage, external AI request, sharing, or booking integration. Downloaded briefs are separate user-owned copies and are not removed when a record is later deleted from LifeOS.

Medical review drafts are keyed by source ID. Changing the source clears the draft and consent, while active requests lock its fields. Responses from an old source cannot populate a new source's draft. Failed confirmations retain the current inputs for correction or retry.

## Trust boundaries

```text
Untrusted browser
   │ Clerk session + validated request (never a trusted userId or key)
   ▼
Next.js Node.js server ── verifies identity ──► Clerk
   │ maps Clerk ID to internal User.id
   │ authorizes + audits within LifeOS
   ├──► PostgreSQL / Prisma (ownership, encrypted domain values, audit ledger)
   └──► PrivateStorage ──► private MinIO or S3/SSE-KMS bucket
                                  ▲
                       short-lived signed PUT only
```

Authentication answers who holds a verified Clerk session. Authorization separately resolves the active internal LifeOS user and scopes every personal-data operation to that internal `userId`. Client input cannot select an owner or storage key.

## Tenant-consistent relationships

User-owned resource models expose compound uniqueness on `(id, userId)`. `DocumentUpload`, `ExtractionJob`, `MedicalRecord`, and `LifeEvent` reference `SourceDocument` through both `sourceDocumentId` and `userId`; `LifeEvent` uses the same pattern for its optional `MedicalRecord` relationship. PostgreSQL therefore rejects a cross-owner link even if application authorization contains a defect. Application-level authorization remains mandatory.

## Upload and quarantine lifecycle

The server validates filename, fixed MIME type, byte size, SHA-256 checksum, and authenticated user. It generates a random user-prefixed key, creates one `DocumentUpload`, and returns a ten-minute presigned PUT plus fixed required headers. Production signatures require SSE-KMS; MinIO uses the same private interface without KMS. Confirmation accepts only the upload ID, resolves the stored key server-side, checks ownership, status, expiry, object size and checksum, consumes the authorization once, and moves the document to `QUARANTINED`. A later malware/content-validation step must move it to `AVAILABLE` or `REJECTED`.
